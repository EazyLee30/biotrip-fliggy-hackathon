# 身体旅行与调整后端升级

验证日期：2026-10-19。本轮未部署；上线前需要依次应用 `0013_body_journey.sql`、`0014_journey_collections.sql`。飞猪查询回执/清理由 `0015_tool_receipts_cleanup.sql` 管理。

## 已实现的行为

- 自评单独持久化，含目的地时区、当地日期、记录时间和来源。1–5 自评与 WHOOP 恢复值分开存储、解释，不相互换算。当目的地过午夜或时区改变，旧记录仍在历史中，但不再充当今天的 `current`。
- 活动有明确的 `planned / in_progress / completed / skipped` 状态。用户操作决定实际进度；模型不能写入或覆盖进度。没有明确状态而已过计划开始时间时保守保留，并提示可标为“未开始”。
- 自动调整、完整候选确认、旧生成保存、手动修改、历史恢复共用保护。调整确认还按服务端当前目的地时钟核对任务提交当地日和 scope 日期；跨午夜即失效，包括旅程尚未开始而 scope 被钳到未来首日的情况。同日确认使用最新分钟再次校验，不能改动等待确认期间已开始的活动。实际进行中、已完成、已跳过项不被改写；自动调整与恢复还保护固定预约。手动改约需明确编辑预约。历史恢复只恢复安排，保留当前进度；恢复会改动已完成活动的内容/时间时拒绝。
- 时间验证覆盖完整的明确 `durationMin` 与已核验交通时长。14:00–17:00 的预约在 15:00 仍占用区间；新增休息从 17:00 后开始。旧活动没有明确时长时按相邻时段保守兼容，不把推算时长当作预约承诺。
- 快速调整不触达模型、库存、地图或 WHOOP，也不消耗规划额度。有可采用调整的候选直接进入待确认；无候选或仅呼吸练习时立即完成，避免占用账号规划槽。确认仍使用同一规划任务版本校验和原子提交。初始候选、增强查询、实际采用是分开的操作。
- 每次采用单独保存 `AdjustmentRecord`，每条记录有自己的 `AdjustmentOutcome`。第二次调整不覆盖第一次的反馈入口。同旅程、同当地日期最近五次反馈影响候选排序；“还是很累”降低相同调整类型的优先级。它不会自动推导长期健康或性格特征。
- 采用调整/重规划及手动/聊天移除活动时，将原活动放进待安排。行程、调整记录、待安排条目在同一 D1 batch 中提交；版本、独立调整/任务标识或手动变更标识共同保护，失败的竞争写入不会留下无效条目。
- 旧反馈入口仍可用；数值反馈同步当天自评，能对应最新独立调整且含明确结果时同步其 outcome。长期记忆继续需要单独明确保存。
- 增强查询按当前需要执行：腿累查询交通，饥饿查询餐食，想安静查询茶馆/当地服务。未选择 WHOOP 或旅行不在近期时跳过健康模型；无来源/路线/健康解释时跳过额外合成，保留确定性建议。

## 接口契约

| 接口 | 输入 | 返回 |
| --- | --- | --- |
| `GET /api/journeys/:id/body-check-ins` | 登录态 | `{checkIns,current,localDate,timezone,asOf}` |
| `POST /api/journeys/:id/body-check-ins` | `{fatigue,stress,tags,consent:true}`，`Idempotency-Key` | 同 GET |
| `PATCH /api/journeys/:id/activities/:activityId/state` | `{version,state}` | `{journey}` |
| `POST /api/journeys/:id/adjustments/quick` | 现有 `AdjustmentRequest`，`includeWhoop:false`，UUID `Idempotency-Key` | `{job,created}`；有可采用调整时 `job.state=awaiting_approval`；无调整或仅呼吸行动时 `completed`；`job.adjustment.strategy=quick` |
| `POST /api/plan/jobs/:jobId` | 现有采用接口，版本和选中 proposal IDs | `{job,journey}` |
| `GET /api/journeys/:id/adjustments` | 登录态 | `{adjustments}` |
| `POST /api/journeys/:id/adjustments/:adjustmentId/outcome` | `{version,feeling,fatigue,stress?,note?}`，`Idempotency-Key` | `{journey,adjustment,checkIn}` |

`feeling` 为 `lighter / same / still_tired`。fatigue/stress 为 1–5 整数或 null。写入均执行账号归属与同源检查。自评与 outcome key 长度为 8–100，支持 UUID；同 key 不同内容返回 409。同 key 同内容重放返回已存结果，不重复增长版本或反馈数量。

内部 `recordBodyCheckIn(accountId,journeyId,raw,key,now?,expectedVersion?)` 的第 6 参数用于聊天确认卡；写入 SQL 同时核对版本。`journeyBodyContext()` 返回 `current`、`recentOutcomes`、`pendingAdjustments`、时间信息，聊天读取的就是页面使用的同一套状态。

## 回归验收

`src/lib/body-journey.test.mjs` 和 `src/lib/adjust/protection.test.mjs` 使用真实纯函数及内存 SQLite 执行 D1 SQL，覆盖：

1. 自评重新读取、重复提交、同 key 改内容、不同账号、未同意、目的地跨午夜、过期版本。
2. 固定 14:00–17:00 预约期间提出休息，候选在 17:00 后插入；完整预约及移动时长不被压缩。
3. quick 无规划额度记录，立即待确认；确认重放只形成一条调整记录。
4. 候选生成后手动改行程，旧候选/旧版本均不能覆盖新内容。
5. 实际已完成活动不可被手动删除或生成改写，未来安排不会错误覆盖进行中的活动；同一旅程最多一项明确进行中。
6. 历史恢复保留当前活动进度；历史内容会修改已完成项时拒绝。
7. 手动移除/自动提前结束同时入待安排；SQL 执行前丢失版本竞争时不写额外记录。
8. 连续两次调整后可给第一次反馈；重复回放不重复反馈/自评；“还是累”改变后续同日排序，跨日不沿用这次短期权重。
9. outcome 丢失版本竞争时不新增反馈/自评；旧反馈接口与新历史一致。
10. 单纯饿了只查餐食，单纯腿累只查路线，空检索结果不会再调用合成模型。
11. 同一个候选被并发使用不同选项确认时，落败的选项不能写入待安排；完整重规划确认也保存被移出的未来活动。

这些测试不调用付费服务，也不证明实际供应商响应延迟或移动端动效表现；这些由单独供应商测试与界面验收覆盖。

## 明确限制

- 活动进度是用户主动标记。没有自动定位/自动判定完成；占用区间仍采用计划的明确时长，未将状态按钮当作精确到店/离店计时器。
- 一账号一次只能有一项运行或待确认规划任务。切换到增强建议或改变快速输入前，前端需先丢弃已有待确认候选。
- 某些全满、临近结束或受固定预约限制的行程无法生成可行调整，返回空候选而不强行改约。当前预约后有空档时有确定性休息方案兜底。
- 完整重规划允许通过预约图卡显式修改未来预约的日期、时分和固定状态，改动仅随最终候选采用；其他固定活动与实际进度仍受保护。若模型额外改变这些活动，会在生成候选或确认时拒绝。
- 反馈排序是可解释的短期规则，尚不是跨旅程学习模型；本轮不会把一次“很累”写为长期偏好。
- 新后台 GET 最多返回最近 60 条自评/调整记录；长期分页尚未加入。

## 预约卡片与重新规划的原子确认

`POST /api/plan/jobs` 可提交顶层 `reservationEdits: [{ activityId, date, time, fixed }]`。只接受当前账户旅程已有活动的标识和这四个字段；不能由客户端改名称、时长、来源或实际进度。前端同时提交规范化的 `trip.itineraryText`，用于兼容新活动与灵活安排；已有预约的身份与约束来自真实 itinerary，不依赖文本序号或同名推测。

准备阶段创建内存影子行程，将显式编辑映射到已有活动，带入真实时长及进度。正在进行、已完成、已跳过的活动不能改动；未明确标记“未开始”的已过开始时间活动沿用原有保护。未来固定预约之间的新区间冲突会立即拒绝；预约移到旧灵活活动时段则允许模型重排该灵活项，最终候选必须重新通过完整时长和交通间隔校验。

授权保留在任务 `request_json`，候选按影子预约的日期、时间和名称匹配回真实 ID，并恢复服务器保存的完整时长与进度。用户预览时原行程与版本不变。采用时读取最新实际行程，重新构造影子基准并校验；只允许该授权范围内的固定预约变化，再通过 SQL 版本 CAS 与任务状态保护原子保存。被明确取消固定限制且从候选移除的活动进入待安排。放弃候选不修改真实预约，也不会操作供应商订单。

旧 `POST /api/plan` 是直接保存入口，任何带 `reservationEdits` 的请求都返回 `409 PLANNING_JOB_REQUIRED`，要求走预览确认流程；不能通过旧入口提前提交预约改动。

旧 itinerary 缺少日期时，服务端使用已保存原旅程的出发日期及双方时区计算原抵达日，供准备、候选与最终采用共用；只在采用时写回补齐的日期。不会使用新请求的旅行日期推定历史。原草稿已经与生成计划不一致，或原始日期/时区不足以可靠推定时，返回 `RESERVATION_DATE_UNKNOWN`；已完成项不能改到新日期。补充三项回归覆盖跨日期变更线、无日期固定项与已完成项的完整确认流程、修改新旅行日期不能移动历史；针对测试 65 项通过。

新增回归包括跨日移动仍保留 ID 与三小时时长、模型伪造进度被丢弃、预览前后实际行程不变、最终采用一次、释放固定状态后移除进入待安排、拒绝未授权的第二个固定项变化、非法字段/未知 ID/重复 ID/超出旅行日期、固定区间冲突、三种实际进度状态保护、确认前并发进度更新、确认中 SQL CAS 竞争不写计划或待安排。2026-10-19 本地全量测试 450 项通过；不调用模型或真实搜索服务，生产模型遵守这些预约约束的成功率尚未实测。
