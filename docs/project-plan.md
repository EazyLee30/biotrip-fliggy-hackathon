# BioTrip 项目计划

**计划基准：2026-09-26**

**目标提交日：2026-10-25（来自当前项目背景；最终以飞猪后台参赛指南为准）**

**产品形态：手机优先、可添加到主屏幕的响应式 PWA + 桌面网页**

## 1. 项目目标

在比赛周期内交付一个可以在手机和桌面体验的真实演示应用：BioTrip 读取当天的身体状态和旅行日程，解释当前行程为什么可能过重，提出保留重要活动、减少移动负担、留出恢复时间的调整方案；用户确认后更新 TREK 行程。需要补充内容时，使用 FlyAI 展示真实飞猪旅行搜索结果及可预订链接。

本项目不以“生成完整旅游攻略”为卖点，而以“原有行程能根据旅客当天状态调整，并且用户看得懂、能确认、能撤销”为核心价值。

## 2. 参赛 MVP 范围

### 必须交付

- 在 TREK 的真实行程页面中增加 BioTrip 体验入口。
- 一份三日东京示例行程，至少包含固定预订、普通景点、步行移动和可调整项目。
- 两个可一键切换的合成身体状态：状态良好和恢复不足；可手工调整演示值。
- “结构稳定 ↔ 随机弹性”连续滑杆，控制可移动行程的范围。
- 可解释的适应计划：锁定预订、提出低负荷交通替代、加入恢复时间、必要时移动一个弹性项目。
- 在写回行程前显示差异预览；用户确认后更新 TREK，界面和地图重新反映结果。
- FlyAI 搜索替代 POI，并展示结果来源、实时性状态和飞猪链接；服务不可用时明确展示备用演示状态。
- iOS/Android 手机浏览器可访问，响应式适配平板和桌面；HTTPS 下支持添加到手机主屏幕并以独立窗口启动。
- 比赛展示材料：可访问 Demo、约 2–3 分钟的核心场景演示、架构与产品说明、运行/体验指引。

### 延后到 MVP 之后

- Whoop、Apple Health、Garmin 等正式 OAuth/设备数据接入。
- 自动下单、自动取消、未经确认的日程变更。
- WorldLens 眼镜相机、GroupMind 多人 Agent、从图片生成目的地。
- 多用户生产账号体系、复杂推荐模型、长期健康画像。
- 全面 fork TREK、重写地图或重做预订系统。

## 3. 手机端与 PWA 验收标准

以 BioTrip 插件在 TREK 的移动应用外壳内工作为验收目标，不只验证桌面缩放：

1. 在约 360 px 窄屏宽度下不出现横向溢出；行程项目、状态卡、理由和操作均能自然换行和滚动。
2. 主要按钮在手机上易于点按；复杂的前后差异以移动友好的卡片/时间线呈现，不依赖 hover、右键或双栏布局。
3. iOS Safari 和 Android Chrome 访问 HTTPS 地址后，可按系统流程添加到主屏幕；从图标打开时进入 standalone 窗口而不是浏览器标签页。
4. 旋转屏幕、键盘弹出、刘海/底部手势区和 TREK 插件 iframe 高度变化时，主要操作仍可见。
5. 桌面宽屏可使用并行的行程、地图和调整详情布局；手机与桌面共用相同行程数据及决策规则。
6. 联网时才能查询 FlyAI 和提交行程变更；断网时展示明确状态，不伪造已保存或已查询的结果。离线体验只在验证 TREK/PWA 实际缓存行为后列入承诺。

## 4. 自适应行为验收

| 场景 | 预期行为 |
| --- | --- |
| 恢复状态良好 | 尽量保留原安排，不为了展示 AI 而强行改行程 |
| 恢复状态不足，结构偏好高 | 预订和时间顺序不变；优先建议更省力的交通和休息时段，不擅自跨天移动项目 |
| 恢复状态不足，弹性偏好高 | 保留预订；可把标记为 flexible 的项目改到当天较晚或次日，并显示保留了什么、改变了什么 |
| 固定活动间隔不足 | 给出冲突提示；不能伪造“可行”方案，也不能覆盖固定预订 |
| FlyAI 无结果或接口失败 | 保留本地演示内容并明确标记为示例；不把样例伪装成实时库存 |
| 用户拒绝建议 | 原行程不变；可以缩小调整范围或改回其中一项 |

身体状态输入目前是产品演示数据，不输出医疗判断。身体状态差异、线路数据和商品数据在界面中应区分来源；交通时间或商品价格若无真实来源，不显示成实时事实。

## 6. 演示脚本

1. 打开手机主屏幕上的 BioTrip 图标，进入东京旅行。
2. 展示今天原计划：若干步行路段、固定预约和一个可移动活动。
3. 将演示身体状态切换为睡眠不足/恢复偏低，并将行程灵活度调整到“结构优先”。
4. 展示引擎说明：哪些预约保持不动、哪段步行建议换交通、插入多少恢复时间；给出预计保留比例，但比例必须从真实变更集合计算，不能写死。
5. 把滑杆调整到更灵活，展示仅移动可调整活动后得到的第二版方案。
6. 预览变更并由用户确认；返回 TREK 行程，展示实际修改和地图同步。
7. 搜索低负荷替代体验，展示来自 FlyAI 的真实结果和飞猪详情链接。

## 7. 风险与应对

| 风险 | 影响 | 先行处理 |
| --- | --- | --- |
| TREK 插件手机 iframe 与 PWA 的实机布局不符 | 影响产品的第一观感和主流程 | 9/26–9/28 先做真实宿主和窄屏 POC，不等主功能完成才查 |
| FlyAI CLI 运行方式不适合 TREK 插件隔离进程 | 商品搜索无法在正确的信任边界内接入 | 先从服务端做一次调用验证；若插件运行时不允许子进程，则单独运行适配服务并收紧网络权限 |
| FlyAI 真实结果/权限/额度不稳定 | 搜索环节现场失败 | 有清楚标记的样例 fallback；现场展示结果来源，不伪造实时数据 |
| 免费 VM 无容量、受区域限制或不能提供稳定 HTTPS | PWA 安装和公开 Demo 受阻 | 第一周完成部署 POC；同时保持本地 Docker 可运行；任何付费部署先确认预算 |
| 修改 TREK 核心带来 AGPL 网络服务义务 | 影响比赛公开 Demo 和源码要求 | 优先插件，不 fork；上线前检查比赛提交要求和所用代码许可边界 |
| 真实健康数据敏感 | 用户隐私和信任 | MVP 使用合成数据，不保存健康历史，不把数据发给 FlyAI |
| P/J 简化导致刻板印象 | 产品个性化体验不准 | 用连续“行程灵活度”参数，允许用户随时改，不推断人格类型 |

## 8. 发布门槛

- 核心演示可重复完成：输入状态 → 生成方案 → 看懂理由 → 用户确认 → TREK 行程改变 → 查询飞猪选项。
- 手机和桌面主流程均可用；PWA 安装路径在目标设备实测。
- FlyAI 结果与样例数据在界面中严格区分；所有写操作由用户确认。
- 体验所需密钥只存在服务端环境中；仓库不含真实凭证和健康数据。
- 比赛要求核对完毕；TREK 与第三方组件的许可说明、归属和源码要求处理完毕。
